# Prompt 迭代记录（迭代证据文档）

## Agent 1 · 解析器

### v1 · 2026-10-05（初版）

**背景**：骨架版的 prompt 只给了 JSON 骨架，没有分段规则。

**Prompt 要点**：
- 给出四段结构：education / experience / skills / projects
- 未约束 null vs 空数组，未约束量化数字保留

**已知问题**（待真机验证后迭代）：
1. 兼职类经历 company 字段写什么不明确（"一对一辅导（科目）"格式是 v1 就定的）
2. 无 "只输出 JSON，不要 markdown 代码块" 约束时，DeepSeek 偶尔包 ```json 围栏导致解析失败
3. 双栏简历的段落顺序错乱（pdfplumber 按 x 坐标逐行提取，左右栏交错）——已加双栏检测警告，解析 prompt 层面的修复待验证

### v2 · 2026-10-06（做实版）

**改动**：
1. 明确 "一个对象，不要数组包裹"
2. 明确 "简历中找不到的字段给空数组，不要输出 null"
3. 明确 "保留原文数字（分数、课时、年限），不得编造"
4. 明确归属规则：兼职/实习/工作都归入 experience
5. 加 "只输出 JSON，不要任何解释或 markdown 代码块"

**机制**（非 prompt，但同属解析可靠性）：
- Pydantic `ResumeStructured` 校验，失败把 ValidationError 喂回 LLM 自纠，最多重试 2 次
- `chat_json` 层面：JSON 解析失败自动重试 1 次（骨架版已有）

**实测效果**（2026-10-07，deepseek-chat，真机）：
- 样本：`tests/fixtures/my_resume.pdf`（单栏，403 字符，1 页）
- 结果：**1 次调用成功，无重试，耗时 3.96s**
- 四段全对：教育（学校/学历/起止时间完整）；两段经历（量化数字 12000 条、90 名学员、11 分提升全部保留无编造）；技能 3 条带应用场景；projects 从自我评价补全 1 条语义相关条目（"找不到给空数组"规则未触发，简历文本含项目暗示）
- 费用意识：单次解析约 600 token 输入 + 300 token 输出，按 DeepSeek 价格约 ¥0.001/次——测试阶段控制调用次数，开发期用 stub，验收时才真机

## Agent 2 · 匹配器

### v1 · 2026-10-07（骨架版）

只给了 JSON 骨架和权重说明，无评分锚点、无 status 枚举约束、无证据规则。

### v2 · 2026-10-09（做实版）

**改动**：
1. 单次调用合并"拆解+比对"两步（两步分开更细但 token 翻倍，节约成本，取舍见下）
2. status 枚举 + Pydantic Literal 校验（hit/partial/miss）
3. score 锚点：hit 70-100 / partial 30-69 / miss 0-29
4. "熟悉 vs 精通"规则：课程学习不得按熟练给分
5. evidence 必须引用简历原文，miss 给空串
6. dimension_scores 是"整体印象分"而非简单平均（重要条目权重高）
7. **总分由代码加权计算，不信 LLM 算术**（LLM 数学不可靠是共识）

**实测效果**（2026-10-09，deepseek-chat，真机，样例简历 × AI Agent 开发实习 JD）：
- 1 次调用成功，15 条要求拆解正确（要求类正确分类）
- 总分 13.2：加权计算验证通过（0.4×20 + 0.3×0 + 0.15×35 + 0.15×0）
- 证据引用全部来自简历原文，无编造

**发现的缺陷（设计考量素材）**：
1. **低匹配场景维度分偏保守**：hard_skill 逐条 4 条中 1 条 45 分，维度分只给 15，低于逐条加权合理区间——LLM 在大量 miss 时有"整体拉低"倾向
2. 简历没写的技能（Git/FastAPI）即便实际掌握也判 miss——**这是期望行为**（只按纸面证据评分，可解释性优先），但对求职者是提醒：简历该写的必须写
3. "每周实习 4 天"判 miss 合理（简历未写每周可实习天数）；但简历明确写了"持续可实习 6 个月"，"能实习 3 个月以上者优先"仍判 miss 且无证据——**有证据未被引用**的反向问题，evidence 质量待 v3 加双向约束（证据必须直接支持要求；要求满足时必须引用证据）

**v3 迭代方向**：维度分与逐条分一致性校验（偏差 >20 分时以逐条加权为准重算）；evidence 相关性约束。

## Agent 3 · 改写器

### v1 · 2026-10-09（骨架版）

单次调用改写全部条目，无流式、无伦理约束（有编造风险）。

### v2 · 2026-10-11（做实版）

**架构取舍（设计要点）——条目级并发流式**：
- JSON 结构化输出与 token 级流式天然冲突（JSON 未闭合无法 parse）
- 改为每条建议独立 LLM 调用 + asyncio.gather 并发，完成一条经 asyncio.Queue 侧信道推一条 SSE
- LangGraph 节点通过 `config["configurable"]["stream_queue"]` 拿队列——同一张图，流式/非流式共用

**伦理红线**：不编造。partial 基于简历素材 STAR 改写；miss 只给占位符模板（X%、N 次、【请填写】）；education 硬门槛与 bonus miss 直接跳过（改不了/编不出）。

**真机实测**（2026-10-11，样例简历 × AI Agent JD）：6 条改写，miss 条目全部占位符模板，零编造。全链路 9.1s。

**真机踩的 2 个坑（LangGraph 经验，值得写进博客）**：
1. **流挂死**：预解析结果传进 `graph.ainvoke`，但线性图的 parser 节点仍要 `resume_text` → KeyError 被 asyncio.create_task 吞掉 → queue 永等。修复：节点幂等跳过（state 已有该节点产出则跳过）+ `asyncio.wait(FIRST_COMPLETED)` 竞争监听图任务与队列，图异常立即冒出。
2. **config 静默丢失**：LangGraph 对节点签名做内省，`config: dict | None` 类型不对 → config 不传 → queue=None → 6 条改写算完却不推送（只发 UserWarning 不报错）。修复：`config: RunnableConfig`（langchain_core.runnables）。教训：框架的"警告"要当错误看。

**v3 迭代方向**：并发节流的 semaphore（6 条并发对 DeepSeek 无压力，但换小供应商要注意）；rewritten 长度约束（部分模板偏长）。

## 全流程实测记录（2026-10-16，样例简历 × 3 JD）

**测试**：`tests/run_e2e.py`（一键回归脚本），单次全量约 25s、约 ¥0.02。

| JD | 总分 | 要求拆解 | 改写 | 全程耗时 |
|---|---|---|---|---|
| AI Agent 开发实习 | 13.2 | 15 条 | 6 条 | 9.1s |
| Python 后端实习 | 17.9 | 14 条 | 6 条 | 9.2s |
| 数据分析实习（教育） | 50.6 | 13 条 | 6 条 | 7.1s |

**评分符合直觉验证**：
- 数据分析 JD 得分最高：简历的统计课程背景（统计学/线性代数）+ Python + 量化实践成果（12000 条数据清洗、90 名学员平均分提升 11 分），与"量化专业优先 + pandas + 指标体系"的 JD 最匹配 ✓
- Agent/后端 JD 低分：简历确实无 LangChain/FastAPI/MySQL 项目证据，按"只认纸面证据"原则应低分 ✓
- 加分项维度（bonus）三 JD 差异明显（0/0/55）：教育行业经验只对数据分析 JD 加分，分类正确 ✓

**发现的新问题（未修，记录在案）**：
1. jd_agent_dev 拆出 15 条 vs python_backend JD 14 条 vs data_analyst 13 条——不同 JD 拆解条数波动大（LLM 粒度自由度），评分可比性受影响。候选修复：prompt 中规定"每条要求必须原子化，不得合并"。
2. 全部 JD 都是 6 条改写——MAX_REWRITES 上限每次都触顶，说明改写需求旺盛（低分简历场景），但上限值合理性未校准。

**结论**：三 Agent 串联、SSE、SQLite 落库、条件边代码路径全部工作正常，达到"可对外展示"状态。
